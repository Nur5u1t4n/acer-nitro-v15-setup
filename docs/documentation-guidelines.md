# Правила документации проекта

Документация здесь — практическая инструкция по установке, настройке и восстановлению
окружения. Цель — быстро найти нужную инструкцию, не поддерживая несколько копий одного
и того же руководства.

## Где размещать README.md

- Корневой `README.md` — краткое описание проекта, ключевые решения и ссылки на разделы.
- README в каталоге раздела, например `windows/README.md` или `docs/README.md`, — обзор
  раздела и навигация по инструкциям в нём.
- README конкретной программы или самостоятельного набора настроек — рядом с файлами
  этой программы. Например, `windows/dotfiles/nvim/README.md`.
- Добавляйте README, когда у компонента есть собственные шаги установки, применения,
  обновления или восстановления. Не создавайте README только ради наличия файла в каждой
  технической папке и не оставляйте пустые заглушки.
- Если программа устанавливается только в составе общего набора приложений и не имеет
  отдельных процедур, опишите её в руководстве этого набора. Не создавайте отдельные
  каталоги и README без самостоятельной пользы для пользователя.

## Разделение ответственности

- README каталога служит оглавлением: объясняет назначение раздела и ведёт к подробным
  руководствам.
- README программы содержит конкретные инструкции только для этой программы.
- Сквозной порядок установки системы или всего окружения описывается в одном главном
  руководстве. В других документах на него ссылаются, а не переписывают шаги.
- Общие правила, применимые ко многим программам, размещаются один раз на подходящем
  обзорном уровне; в README компонентов оставляются ссылки и важные локальные отличия.
- Списки пакетов, расширений и серверов поддерживаются рядом с конфигурациями, которые
  их используют. Не дублируйте их в нескольких README, если достаточно ссылки на источник.

## Шаблон README программы

Включайте только подходящие конкретному компоненту разделы:

1. **Назначение и состав** — что настраивает этот компонент и какие файлы репозитория
   относятся к нему.
2. **Требования** — необходимые программы, версии, доступ к сети или другие зависимости.
3. **Установка и применение** — точные команды и ожидаемый результат; укажите, если
   применяется общий скрипт и какие ещё настройки он изменяет.
4. **Первый запуск и проверка** — необходимые начальные действия и команды проверки.
5. **Обновление** — как обновлять программу, плагины или конфигурацию, если это отличается
   от обычного механизма обновлений.
6. **Повторная установка и восстановление** — как восстановить конфигурацию после удаления
   программы или её пользовательских файлов; где искать резервную копию.
7. **Типичные проблемы** — только проверенные решения и ссылки на официальную документацию.

## Требования к содержанию

- Пишите по-русски, кратко и пошагово; команды приводите в готовом для копирования виде.
- Используйте фактические имена файлов, команды и пути из текущей конфигурации.
- Отмечайте потенциально разрушительные действия и сообщайте, какие данные они затрагивают.
- Различайте файлы конфигурации в репозитории, пользовательские настройки и скачиваемые
  данные/кэш программы.
- Для изменяемых внешних интерфейсов предпочитайте ссылки на официальную документацию;
  указывайте проверенную дату или версию, если инструкция привязана к ним.
- Не публикуйте секреты, токены, приватные ключи или персональные данные без необходимости.
- При изменении способа установки, расположения файлов или настроек обновляйте связанные
  инструкции и ссылки в README родительского каталога.
